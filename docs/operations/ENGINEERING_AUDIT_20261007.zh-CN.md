## 部署及迁移

新版本需要先创建 `stored_asset` 表；init.sql 和 ArchitectureDatabaseUpgrade 使用相同结构。首次部署启用既有 `ARCHITECTURE_MIGRATION_ENABLED`，确认重复安全迁移及服务启动后关闭。不要跳过表创建，也不要删改现有业务/历史对象。

Mongo 不需要新增 customSchedule 的 createIndex 权限；grade/schedule 既有权限与索引保持。旧新闻 `_class` 可按明确目标类型读取，测试确认不改写原文档。遇到重复 customSchedule 用户记录停止其修改，先核对数据，不能自动合并/删除。

临时对象最长 PUT 15 分钟、ticket 20 分钟，清理只处理超过 20 分钟的 PENDING/DELETING，每批最多 50 项；加锁后再次核对状态/时间，避免删除被新上传续期的对象。历史 MISSING 缓存 1 小时后重查。图片限制同时包括现有字节上限和 1600 万像素；JPEG/PNG/GIF/BMP 解码验证，WebP 与音频验证文件/容器特征，未加入完整媒体转码器。

## 请求日志与演示环境留存收尾

本轮只修改后端日志和相关测试，不修改 Web/客户端产品代码、样式、排版或数据库结构。请求事件保留 requestId、HTTP 方法、Spring 路由模板、代码处理方法、控制器结果、异常类型和耗时。原始路径、查询/表单/JSON 正文、上传内容、IP 和客户端 headers 不进入请求事件；不再依赖参数名称黑名单猜测正文是否敏感。

直接及 ResponseEntity 包装的 JsonResult(false)、HTTP 错误响应、抛出异常均记录 FAIL，业务返回及异常传播保持原行为。SlowRequest 使用单调时钟，指标仍只用有界 method/handler 标签，阈值保持 800ms；QueryLog 的 1500ms 是业务查询耗时阈值，并非逐条 SQL 执行计划。请求编号仅复用 1–64 位 ASCII 字母、数字、点、横线和下划线，其他值生成完整 UUID；正常或异常退出均恢复原 MDC。async/provider/campusSync 三个线程池只传播 requestId，并在任务退出时恢复工作线程上下文；定时任务不制造 HTTP 请求编号。

全局异常日志保留类型和堆栈位置，不输出异常 message、cause message 或原始 Throwable；反馈 SMTP 单独记录异常和直接 cause 类型，不记录邮箱、凭据、邮件正文或上游返回正文，不自动重发。SQL 日志默认 INFO，删除无文件 appender 却声明 logging.file.name 的误导配置；Logback 仍输出控制台，避免 Native Image 编译期文件描述符问题。这里描述的是本轮请求/全局异常/反馈邮件日志边界，不表示已逐个证明所有历史服务 logger 均无敏感内容。

## Astra 两项 P1 定向整改

本阶段处理旧注销清理与同用户名重新注册的竞态、Provider 熔断后无法恢复探测两个已确认缺陷，不修改前端或扩大到其他审查项。Provider 取消 OPEN 状态提前跳过，由现有 executeSupplier 许可机制控制拒绝、HALF_OPEN 探测和恢复，不自动重置断路器。回归测试使用可控时钟，同一实例连续失败熔断、等待期内降级、到期后恢复成功。

注销清理的领取、跨存储删除及完成/重试更新放在 appTransactionManager 的独立 REQUIRES_NEW 事务内，全过程持有任务主键行锁；提交后回调使用独立连接，避免依赖已提交事务的资源。新账号初始化使用 READ_COMMITTED，在等待既有 app_user 锁后重新读取身份，按任务主键锁定并检查所有未完成清理；任务未完成时拒绝注册，不保存登录证书或签发 JWT。锁定只针对该任务，不增加全队列锁、数据库表或依赖。HTTP 登录返回 409、业务码 40901，并保留响应封装和多语言提示；OpenAPI 补齐这一返回。

对于修复前已出现的“旧任务未完成、同用户名已有 ACTIVE 账号”，worker 停止资源删除，任务保留 PENDING，error_code=ACTIVE_USERNAME_CONFLICT，日志记录同一稳定错误码。此情况需要按新旧身份核对，不能自动标为注销完成；本轮没有查询或修改真实账号。队列仍沿用既有定时重试和失败类型记录。

新增隔离 MySQL 回归覆盖多个未完成任务、失败后的用户名保留、清理中注册阻塞且其他用户名可登录、过期领取的重复 worker、提交后独立事务落库、登录等待期间的注销改名及修复前账号复用保护。校园登录、Redis/Mongo/R2 清理均使用合成替身，测试不执行真实账号注销或供应商业务。充值无长期密码的 NPE、WebSocket 发送串行化两项 P2 保留为后续，未计为已修复。


## Astra 两项 P2 定向整改（2026-10-08）

充值二次验证复用现有 verifyCurrentPassword，以独立客户端、隔离 cookies 执行新鲜校园 CAS 验证，删除 ChargeRequestController 对 UserMapper 和数据库长期密码比较的依赖。正确密码才进入原有幂等/订单/充值流程；错误密码、认证不可用均在创建订单和调用充值上游前失败。不会为充值保存长期凭证，也不改变既有未知付款结果和禁止盲重提交的处理。沿用校园系统已核实的协议配置，没有要求外部系统升级。

WebSocket 的 ready、pong、业务事件统一使用 SocialRealtimeHub.sendToSession，状态检查和写入共享同一 session monitor。认证登记前先取得该锁，让 ready 先于新登记后的业务推送发送。IOException、IllegalStateException 只影响该连接：移除登记、尝试关闭、取消失败 ready/pong 的周期复核，不阻断其他连接，不传播到已提交事务的调用方。日志只记录异常类型，不写传输异常正文、JWT 或业务消息。原事务 rollback 零成功事件和账号/会话复核保留。

新增回归使用 loopback HTTP CAS fixture 与合成支付替身，验证无可用保存密码的成功/失败、已缓存密码不能绕过新鲜验证、CAS 不可用零订单；WebSocket 阻塞 fixture 验证发送互斥、ready 的监视器与业务推送一致、发送失败注销与定时复核清理，并用真实 H2 事务验证提交成功后故障连接不会改变结果、正常连接持续收到事件。没有真实充值、校园账号操作或前端样式修改。
